CORPFLOW · BEFORE
The broken schema had no isolation boundary
CREATE TABLE users ( id SERIAL PRIMARY KEY, name VARCHAR(100), email VARCHAR(100), salary DECIMAL(10,2), role VARCHAR(20) ); CREATE TABLE projects (... owner_id REFERENCES users(id));
Audit findings
No tenant_id on any table
Salary and billing fields exposed
Roles unconstrained
Owner foreign key could cross tenants
No tenant indexes or isolation tests
Original code shown from original-schema.sql1 / 5
CORPFLOW · DECISION 01
Anchor every record to a tenant
CREATE TABLE tenants (...); CREATE TABLE users ( id SERIAL PRIMARY KEY, tenant_id INTEGER NOT NULL REFERENCES tenants(id), name VARCHAR(100) NOT NULL, email VARCHAR(100) NOT NULL, role VARCHAR(20) NOT NULL CHECK (role IN ('admin','manager','user')), salary DECIMAL(10,2), UNIQUE (tenant_id, email) ); Every tenant-specific row now carries the isolation key.
Decision: tenant_id is mandatory, not optional2 / 5
CORPFLOW · DECISION 02
Make relationships tenant-aware
CREATE TABLE projects ( id SERIAL PRIMARY KEY, tenant_id INTEGER NOT NULL REFERENCES tenants(id), title VARCHAR(200) NOT NULL, owner_id INTEGER NOT NULL, CONSTRAINT projects_owner_same_tenant FOREIGN KEY (tenant_id, owner_id) REFERENCES users(tenant_id, id) ); The database rejects a project owner from another tenant. CREATE INDEX idx_projects_tenant_owner ON projects(tenant_id, owner_id);
Decision: IDs alone are not a safe boundary3 / 5
CORPFLOW · DECISION 03
Filter responses by role before sending
// Never return raw rows res.json(users.rows) // Map a safe response const base = { id: user.id, name: user.name, role: user.role } if (req.user.role === 'admin') { base.salary = user.salary } return base
